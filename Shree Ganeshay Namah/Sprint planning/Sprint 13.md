## The independent re-review of Sprint 12 this sprint's own instructions required

Not just trusting Sprint 12.md's own write-up — re-read the actual new cancellation/ledger-reversal/rider-decline backend RPCs and routes with fresh eyes, same discipline every sprint since Sprint 6 has applied to the one before it. **This found two real issues, both fixed before any of this sprint's own new work started:**

1. **`forceReassignRider` (lib/riderAssignment.ts) was the one cross-table mutation in this entire codebase that wasn't atomic.** Every other cross-row mutation in this project — `rpc_place_order` through `rpc_cancel_order`/`rpc_rider_decline_order` — is a single `SECURITY DEFINER` SQL function for exactly this reason (§5.1's own standing rule). This one function, added in Sprint 12 for the shop's "this rider isn't responding, find someone else" manual escape hatch, instead ran its read-then-release-then-clear-then-log sequence as four separate, unwrapped `db.execute` statements. Two concurrent force-reassign calls on the same order could both read the same `rider_id` and both attempt the release — self-correcting in practice (`rpc_assign_rider`'s own `FOR UPDATE` lock still serializes the actual reassignment correctly, so no double-assignment could ever result) but a real, disclosed race, and a real inconsistency with this project's own established convention. **Fixed:** wrapped the read (now `SELECT ... FOR UPDATE`) and the three writes in `db.transaction()` — checked directly, not assumed, that this is real and safe here: `drizzle-orm@0.36.4`'s postgres-js `transaction()` delegates to `postgres`'s own `client.begin()`, which holds one connection for the whole callback, exactly what `lib/db.ts`'s own Supavisor **transaction-mode** pooler is built to support. This is the first use of `db.transaction()` anywhere in this backend — a genuinely new pattern, used because it was the right tool, not reached for casually. `assignRider()` itself stays outside the transaction (already atomic on its own, and it makes a real outbound HTTP call for the push notification — holding a DB transaction open across that would be a new, unrelated problem).
2. **The shop-initiated cancel route (`POST /shop/shops/:shopId/orders/:orderId/cancel`) had no route-layer membership gate at all**, unlike every other shop-team write path in the same file — `advance-status` checks `isShopMember` and `assign-rider` checks `isShopWriter` before touching the database; this handler went straight from an order lookup to `rpc_cancel_order`, relying entirely on that RPC's own `NOT_SHOP_MANAGER` check deep inside a locked transaction. Not a security hole (the RPC's own check is real and correctly ordered, per Sprint 12's own bug #3 fix), but an inconsistency, and it meant a caller with no relationship to a shop at all could still cause an order row to be locked before being told no. **Fixed:** added the same `isShopWriter` gate the assign-rider route already uses (same owner/staff tier — cancelling is an operational decision, not the broader "advance status" right §5.3 gives every `member_role`).

Everything else re-read clean: `migrations/046`–`049` in full (the ledger-reversal shape/CHECK, `rpc_cancel_order`'s authorization-before-status ordering, `rpc_rider_decline_order`'s accept-gate and exclusion-list handling, `rpc_expire_stale_rider_assignments`'s latest-assignment CTE and per-order exception isolation), `lib/ledger.ts`/`lib/cancellation.ts`, the `proximity_web` admin settings/discounts/ledger pages, and the mobile cancel/decline UI (`shop_orders_screen.dart`, `rider_home_screen.dart`, `order_confirmation_screen.dart`'s cancel action) all held up against their own stated design. Both fixes above are re-verified: `deno check supabase/functions/api/index.ts` clean after each.

## The design-system audit, in full

Checked the actual shipped screens against §6's literal spec, not just `app_theme.dart`:

- **Colors.** `AppColors.brand`/`accent`/`urgent`/`cream`/`ink`/`inkSoft`/`line` match §6's literal hex values exactly. Grepped the whole app for any hardcoded `Color(0xFF...)` outside the theme file — zero found; every screen consistently reaches for `AppColors.*`. The one real deviation was the four `Colors.red` instances above, now fixed.
- **Fonts.** Baloo 2 (display: `headlineLarge`/`Medium`/`Small`, `titleLarge`) + Plus Jakarta Sans (everything else) via `google_fonts`, matching §6 exactly — unchanged since Sprint 1, still correct.
- **Tabular-nums.** Missing entirely; fixed centrally (above).
- **Contrast — measured, not guessed.** Computed real WCAG relative-luminance contrast ratios for the actual pinned hex pairs (Node, standard WCAG formula):

  | Pair | Ratio | WCAG AA (normal text, 4.5:1) |
  |---|---|---|
  | ink (#221B1A) on cream (#FBF7F2) | 15.88:1 | Passes (comfortably clears AAA's 7:1 too) |
  | white on brand (#0F7A5C) | 5.30:1 | Passes |
  | brand on cream | 4.97:1 | Passes |
  | inkSoft (#7A7370) on white | 4.65:1 | Passes (barely) |
  | **inkSoft on cream** | **4.36:1** | **Fails** — by a small margin, on this app's actual background color |
  | **urgent/terracotta (#E4572E) on cream, as text** | **3.45:1** | **Fails** |
  | **urgent on white, as text** | **3.68:1** | **Fails** |

  `urgent`/`success`/`accent` as **icon colors or ~16%-opacity badge-background fills** (the far more common usage — e.g. `order_history_screen.dart`'s status chips render dark `ink` text over a tinted background, not colored text) clear the separate, lower WCAG 1.4.11 non-text/UI-component threshold (3:1) comfortably. The real gap is specifically **`inkSoft` and `urgent` used as actual small body/label text** — and that's a real, current pattern in this app: 45 call sites across 27 files style a `Text` widget's color with one of these three tokens, many of them exactly the "metadata caption" and "this went wrong" text the contrast rule is meant to protect. **Not fixed here, deliberately:** both are pinned, named brand values in §6, shared verbatim by `proximity_web`'s `globals.css` (`--muted-foreground`/`--destructive`) specifically so the two apps' brand colors stay one source of truth, not two approximations. Touching either hex is a brand-identity decision, not a "polish" one — the same bar this project has always held for genuinely open calls (Razorpay-vs-PayU pricing, the discount-absorption direction, the cancellation state machine) rather than picking silently on your behalf. **Flagged with exact numbers and a concrete recommended path**, not silently left for someone to rediscover: introduce a dedicated darker variant (e.g. an `AppColors.urgentText` distinct from the badge/icon `AppColors.urgent`) for on-light-background text specifically, leaving the existing token's icon/badge use untouched. Needs a real decision from whoever owns this design system, not an autonomous hex change.
- **Tap targets.** Every `IconButton` in this app defaults to (or, via `VisualDensity.compact`, shrinks somewhat below) Material's 48×48dp recommendation; the smallest — the cart line's own quantity stepper (`cart_item_tile.dart`, hard-constrained to a 32×32 `SizedBox`) — still clears the newer, actually-enforceable WCAG 2.5.8 minimum (24×24 CSS px) with room to spare. **Checked, not changed:** bumping any of these risks a real layout regression on the ~400px-wide phone width this project is committed to supporting, and this session has no device or emulator to visually confirm a change doesn't overflow (the same standing gap every sprint since Sprint 4 has carried) — so this is reported as "passes the enforceable bar, below the softer Material recommendation in a few compact spots," not silently fixed by guessing at a size that can't be seen.

## The Crashlytics decision

Built, but flagged with a real, disclosed asymmetry from every other integration in this project — read `lib/core/crash/crash_reporting_service.dart`'s own header for the full account, short version:

Every prior third-party integration in this project (Razorpay, FCM/APNs) is code-complete today and is honestly, simply "blocked on real credentials arriving" — the moment a real account exists, the existing code starts working with no further changes. **Crashlytics is not that**, checked directly against Firebase's own current Flutter setup docs before assuming otherwise: basic crash reporting needs the `com.google.firebase.crashlytics` Gradle plugin added to the Android build, which `flutterfire configure` adds automatically and which this project has deliberately never run (same Sprint 11 reasoning as ever — it needs a live `firebase login` + a real project neither of which exists, and hand-adding the plugin with no matching `google-services.json` would break the next Android build for a reason unrelated to any Dart code here). Manual `FirebaseOptions` — the path that made FCM a complete, real integration without the CLI — does **not** substitute for what the Gradle plugin does (embedding build/mapping metadata so Crashlytics can symbolicate a crash). So: the Dart-side wiring here is real, ready, and will start sending Dart-level error reports the moment real Firebase config lands — but full crash reporting still needs `flutterfire configure` (or an equivalent, deliberate native-build change) to run for real, on top of that, unlike every other "just add credentials" gap this project has carried. Flagged this plainly, in the code and here, so a future session doesn't treat "the Firebase project now exists" as the whole unblock the way it correctly would for FCM.

## The Sentry decision

§3.2 named this "Optional... complements mobile-only Crashlytics" and asked this sprint to decide, not defer again. **Decided: worth doing for real, not left optional.** This backend's `index.ts` has had exactly one place every unhandled route error already funnels through since Sprint 1 (`app.onError`) — wiring real error tracking onto an already-existing seam is a small, high-value addition, not new plumbing, and there was no real reason left to keep calling it optional.

Two real things checked live before writing any code, not assumed:
- **Version:** npm's bare `latest` tag for `@sentry/deno` is `10.74.0`, but Supabase's own current, maintained Sentry-monitoring guide (`supabase.com/docs/guides/functions/examples/sentry-monitoring`) pins `npm:@sentry/deno@^8` specifically for Edge Functions — Supabase, not this project, is the actual authority on what their production Edge Runtime supports, so `@^8.55.2` (the current 8.x) was pinned instead of grabbing whatever "latest" happens to mean on npm generally. `deno check` was run directly against the real, downloaded 8.55.2 package (not assumed) before writing anything against `Sentry.init`/`.captureException`/`.withScope`/`.flush`/`.setTag`.
- **A real, documented limitation, not discovered the hard way:** Supabase's own guide states the Sentry Deno SDK doesn't instrument `Deno.serve`, so there's no automatic per-request scope separation on this runtime. Mitigated exactly the way that guide recommends — `captureError()` wraps every capture in `Sentry.withScope`, attaching that one request's own method/path explicitly, rather than relying on automatic scoping that doesn't exist here.

Deliberately no tracing/profiling (`tracesSampleRate`/`profilesSampleRate` both left at Sentry's own default of 0) — this sprint's ask is error tracking, not APM, and Sentry's pricing is quota-based on transaction volume; turning on tracing nobody asked for would be speculative scope and a real cost surprise, not a free addition.
